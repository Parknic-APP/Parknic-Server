# 서버 전환 계획: 임시 서버(AWS) → 사용자 서버(GCP)

작성일: 2026-11-23 · 상태: **초안 (사용자 확인이 필요한 항목은 ❓로 표시)**

## 1. 목표와 범위

- 출시된 앱 1.0.0이 쓰는 임시 서버(`https://parknic-dev.duckdns.org`, AWS)를 이 저장소의 서버로 교체하고, 새 서버는 **GCP**에서 운영한다.
- 앱 사용자가 로그인/체크인/리뷰를 하는 동안 **눈에 띄는 중단 없이** 옮기는 것이 목표다.
- 범위 밖: 카카오 로그인(보류), 앱의 신규 기능(도움돼요, 다른 유저 프로필 등).

## 2. 현재 상태

### 2-1. 임시 서버 (알려진 것)
| 항목 | 내용 |
|---|---|
| 호스트 | AWS EC2 (`ubuntu@15.135.248.111`), SSH는 보안 그룹에 등록된 IP에서만 접속 |
| 도메인 | `https://parknic-dev.duckdns.org` (DuckDNS) |

| 설정 | `~/parknic/.env`, 특히 `REVIEW_MODE`(다음 심사 제출 때 `true`, 통과하면 `false`) |

| 앱 | 1.0.0이 위 도메인을 사용 (Release `API_BASE_URL`) |

### 2-2. 임시 서버에서 확인해야 하는 것 ❓
사용자가 SSH로 읽기 전용 명령을 실행해서 확인한다 (6절 참고). 확인 전에는 아래가 **가정**이다.
- DB 종류와 스키마 (이 저장소의 `V1`과 다를 수 있음), 사용자/배지/리뷰 건수
- 로그인 방식이 Apple 실검증인지, JWT 시크릿과 토큰 형식
- 앱 1.0.0이 호출하는 엔드포인트와 응답 필드 (새 서버와 호환되는지)

### 2-3. 새 서버 (이 저장소)
**완료**: Apple 로그인(실토큰 검증), 로그아웃/토큰 재발급, 프로필/닉네임/탈퇴(Apple revoke 포함), 캐릭터, 주변 공원/상세/리뷰 좋은 공원, 체크인(시작/현재/취소/실패/완료), 배지·업적·주간 랭킹, 리뷰(작성/목록/수정/삭제/신고/내 리뷰), 차단, 통계, 도감, 자정 체크인 정리 스케줄러, 운영 컨테이너 이미지.

**빈틈** (전환 전에 메워야 하거나 결정이 필요한 것)
| 빈틈 | 영향 | 전환 전 필수? |
|---|---|---|
| `/terms`, `/privacy`, `/support` 페이지 없음 | 앱/스토어가 URL로 사용. 없으면 심사와 앱 내 링크가 깨짐 | **필수** |
| `REVIEW_MODE` 스위치 없음 (`review_only` 공원을 항상 숨김) | 다음 앱 심사에서 심사관이 한국 밖에서 체크인할 수 없음 | 다음 심사 제출 전 필수 |
| HTTPS/도메인 | 앱은 HTTPS가 필수 (ATS) | **필수** |
| 백업/복구 절차 | 데이터 유실 시 복구 불가 | **필수** |
| 모니터링/알림 (장애, 5xx, 디스크) | 장애를 사용자 제보로 알게 됨 | 권장 |
| 임시 서버 데이터 이전 | 기존 사용자의 계정/배지/리뷰 | 방침 결정 필요 (4절) |
| 카카오 로그인 | 앱에 버튼은 있으나 서버 없음 | 앱에서 버튼을 숨기기로 결정 필요 ❓ |
| Apple revoke 실계정 연동 | 코드는 완료, Team ID/Key ID/`.p8`을 넣어야 동작 | 계정 삭제 기능 심사 전 필수 |

## 3. GCP 구성 선택지

세 가지를 비교한다. 비용은 변동이 있으니 **공식 요금 계산기로 확인**하고, 여기서는 상대 비교만 적는다.

| | A. VM + docker compose (앱과 DB 컨테이너) | B. VM + Cloud SQL | C. Cloud Run + Cloud SQL |
|---|---|---|---|
| 구성 | Compute Engine VM 1대에 `docker-compose.prod.yaml` 그대로 | VM에 앱 컨테이너, DB는 Cloud SQL(PostgreSQL) | 앱은 Cloud Run, DB는 Cloud SQL |
| 비용 | 가장 낮음 | 중간 (Cloud SQL 월 고정비) | 중간 (Cloud SQL + 요청 기반) |
| 지금 코드와 맞는 정도 | **그대로 동작** (이미 검증한 구성) | 설정만 변경 (`DB_URL`) | 변경 필요 (아래) |
| `@Scheduled` 자정 정리 | 문제 없음 | 문제 없음 | **보장 안 됨**: 요청이 없으면 인스턴스가 0으로 줄 수 있음. 최소 인스턴스 1 + CPU 상시 할당 또는 Cloud Scheduler가 호출하는 정리 엔드포인트 필요 |
| DB 백업/HA | 직접 (`pg_dump` + 스냅샷) | **자동 백업, 시점 복구, HA 선택** | 자동 |
| HTTPS | 직접 (Caddy 등 리버스 프록시) | 직접 | **자동** (관리형 인증서, 도메인 매핑) |
| 운영 부담 | VM 패치와 DB 직접 관리 | VM 패치만 | 가장 적음 |
| 스케일 | 수직 확장, 단일 장애점 | 수직 확장, DB는 관리형 | 자동 수평 확장 (DB 연결 수 주의) |

**추천: 처음에는 A**, 이유는 다음과 같다.
1. 컨테이너 구성을 이미 로컬에서 검증했고 **코드 변경 없이** 올라간다.
2. 자정 스케줄러, Flyway 시작 시 실행 같은 가정이 그대로 유지된다.
3. 비용이 가장 낮고, 학습/포트폴리오 목적에서 "서버 한 대를 직접 운영해 본다"는 가치가 있다.

사용자 수가 늘거나 DB 백업/복구 책임이 부담되면 **B로 DB만 옮긴다** (`pg_dump`로 이전 가능). C는 `@Scheduled` 의존 구조를 바꿔야 해서 지금은 권하지 않는다.

A를 택할 때의 최소 구성
- VM: 작은 인스턴스(예: e2-small급)부터 시작, 디스크는 SSD, **고정 외부 IP**
- 방화벽: 80/443만 공개, 22(SSH)는 본인 IP만, **5432는 열지 않음** (이미 compose에서 비공개)
- HTTPS: VM 앞단에 Caddy(자동 인증서) 컨테이너 추가 → 8080은 호스트에 공개하지 않고 Caddy만 접근
- 비밀값: GCP Secret Manager에서 읽어 `.env`로 주입하거나 VM에서 `.env`를 `chmod 600`으로 관리 (`JWT_SECRET`, DB 비밀번호, Apple `.p8`)
- 백업: 매일 `pg_dump` → Cloud Storage 버킷(보관 기간 설정) + VM 디스크 스냅샷 일정
- 모니터링: Cloud Monitoring 업타임 체크(`/actuator/health`) + 알림 이메일

## 4. 전환 방식과 데이터 방침

### 4-1. 도메인/앱 계약
앱 1.0.0은 `parknic-dev.duckdns.org`를 하드코딩하고 있다. DuckDNS는 IP만 바꾸면 되는 동적 DNS라서 **같은 도메인을 새 서버 IP로 돌릴 수 있다**.

| | A. 같은 도메인 인계 | B. 새 도메인 + 앱 업데이트 |
|---|---|---|
| 앱 업데이트 | 불필요 | 필요 (심사 대기) |
| 전환 시점 | 원하는 때 즉시 | 앱 업데이트 배포 후 (사용자가 업데이트할 때까지 병행) |
| 요구 조건 | **새 서버가 1.0.0의 요청/응답 계약과 호환** | 서버 두 대를 한동안 병행 운영 |
| 롤백 | DNS를 다시 옛 IP로 (TTL만큼) | 쉬움 (옛 서버가 계속 살아 있음) |
| 위험 | 1.0.0과 계약이 다르면 앱이 깨짐 | 업데이트 안 한 사용자가 옛 서버에 남음 |

**권장**: 먼저 호환성 검증(2-2)을 하고, 호환되면 A, 아니면 B. 호환성은 `fe/docs/api-spec.md`와 1.0.0 앱이 실제로 쓰는 엔드포인트를 비교해서 판단한다 ❓.

### 4-2. 데이터 이전 ❓ (사용자 결정 필요)
| | 이전한다 | 새로 시작한다 |
|---|---|---|
| 사용자 경험 | 기존 계정/배지/리뷰가 그대로 | 첫 로그인 시 신규 가입으로 보임, 배지/리뷰 소실 |
| 작업량 | 큼: 스키마 매핑과 변환 스크립트, 검증 | 작음 |
| 위험 | 변환 오류, 전환 중 쓰기 유실 | 사용자 불만, 스토어 리뷰에 영향 |
| 필수 조건 | 임시 서버의 `provider`/`provider_id`가 Apple `sub`와 같은지 확인 (불일치하면 같은 사람이 새 계정으로 보임) | 앱 내 공지 또는 스토어 노트 |

이전하는 경우의 흐름: 임시 서버 DB를 `pg_dump` → 로컬/스테이징에서 변환 스크립트(`INSERT ... SELECT`) 작성과 검증 → 전환 당일 쓰기를 멈추고 한 번 더 덤프 → 변환 적재 → 건수/샘플 대조.

## 5. 전환 순서 (체크리스트)

### 사전 준비 (며칠 전)
- [ ] 2-2의 임시 서버 현황 조사, 앱 계약 비교표 완성
- [ ] GCP 프로젝트, VM, 고정 IP, 방화벽, Secret Manager 준비
- [ ] 새 서버 배포 (`docker-compose.prod.yaml` + Caddy), HTTPS 확인, `/actuator/health` 업타임 체크 설정
- [ ] `/terms`, `/privacy`, `/support` 구현과 배포 (임시 서버와 같은 내용)
- [ ] `JWT_SECRET`, `APPLE_CLIENT_ID`, Apple `.p8`(Team ID, Key ID) 설정, 개발용 로그인 꺼짐 확인
- [ ] 공원 데이터 적재 (`parknic-data/parks.csv`, 17,012건), `review_only` 공원 처리 방침 확인
- [ ] 백업 일정과 **복구 연습** (백업에서 실제로 되살려 보기)
- [ ] 실기기로 새 서버에 Apple 로그인, 체크인, 탈퇴(revoke)까지 한 번 통과

### 전환 당일
- [ ] (이전하는 경우) 임시 서버를 읽기 전용/점검 모드로 전환하거나 짧은 점검 시간 공지
- [ ] (이전하는 경우) 최종 덤프, 변환, 적재, 건수와 샘플 대조
- [ ] DuckDNS를 새 서버 IP로 변경 (A 방식), 변경 전에 TTL 확인
- [ ] 임시 서버를 **끄지 않고 유지** (롤백용)

### 전환 직후
- [ ] 앱(Release 빌드)으로 로그인, 체크인 시작/완료, 리뷰, 탈퇴 확인
- [ ] 서버 로그의 5xx, `unexpected error`, Apple 검증 실패 건수 감시 (1~2시간)
- [ ] 이상 없으면 24~48시간 뒤 임시 서버 종료 (스냅샷 보관)

### 롤백
- DuckDNS를 옛 IP로 되돌린다. 새 서버에서 전환 후에 쌓인 데이터(배지, 리뷰)는 옛 서버에 없으므로 **되돌리면 그 구간의 데이터가 사라진다**. 그래서 전환 직후 짧은 시간 안에 판단하고, 문제가 데이터 쓰기와 관련되면 새 서버를 읽기 전용으로 두고 원인을 먼저 확인한다.

## 6. 임시 서버 현황 조사 (사용자가 읽기 전용으로 실행) ❓

```bash
ssh -i ~/.ssh/parknic-key.pem ubuntu@15.135.248.111
cd ~/parknic

docker compose -f docker-compose.prod.yaml ps
grep -o '^[A-Za-z_]*=' .env                       # 변수 이름만 (값은 출력하지 않음)

# DB 사용자/이름은 compose 파일에서 확인해서 바꿔 넣기
docker compose -f docker-compose.prod.yaml exec db psql -U <DB사용자> -d <DB이름> -c '\dt'
docker compose -f docker-compose.prod.yaml exec db psql -U <DB사용자> -d <DB이름> \
  -c "select 'users', count(*) from users" -c "select 'badges', count(*) from badges" -c "select 'reviews', count(*) from reviews"

docker ps --format '{{.Names}} {{.Image}} {{.Ports}}'
for p in terms privacy support; do curl -s -o /dev/null -w "$p %{http_code}\n" https://parknic-dev.duckdns.org/$p; done
```

## 7. 위험과 대응 (상위 3개)

1. **앱 1.0.0과 새 서버의 계약 불일치**로 전환 후 앱이 깨진다. → 전환 전에 엔드포인트별 요청/응답 비교표를 만들고, 실기기(또는 시뮬레이터에 1.0.0 빌드)로 전체 흐름을 새 서버에서 돌려 본다. 호환이 안 되면 B 방식.
2. **데이터 이전 오류 또는 전환 중 쓰기 유실**로 사용자의 배지와 리뷰가 사라진다. → 변환 스크립트를 스테이징에서 검증하고, 전환 시 쓰기를 멈춘 상태에서 최종 덤프를 뜬다. 임시 서버와 그 DB를 전환 후 최소 2일 보존한다.
3. **단일 VM 장애/디스크 손상**으로 서비스와 데이터를 잃는다. → 매일 `pg_dump`를 외부(Cloud Storage)에 보관하고 복구를 한 번 연습한다. 업타임 알림으로 장애를 빨리 알고, 필요해지면 DB를 Cloud SQL로 옮긴다.

## 8. 결정이 필요한 것 ❓

- [ ] 구성: A(VM + 컨테이너 DB, 추천) / B / C
- [ ] 전환 방식: 같은 도메인 인계(A) / 새 도메인(B) — 계약 호환성 확인 후
- [ ] 기존 사용자 데이터: 이전한다 / 새로 시작한다
- [ ] 카카오 버튼: 앱에서 숨긴다 / 서버를 나중에 만든다
- [ ] 다음 서버 작업의 우선순위: `/terms`·`/privacy`·`/support` → `REVIEW_MODE` → 백업/모니터링

## 9. 다음 서버 작업 (제안 순서)

1. **약관/개인정보/지원 페이지**: 정적 페이지로 서버가 제공 (`/terms`, `/privacy`, `/support`)
2. **심사용 공원 스위치(`REVIEW_MODE`)**: `parknic.review-mode` 설정이 `true`일 때만 `review_only` 공원을 주변 조회와 체크인에서 허용
3. **운영 로그/모니터링**: 요청 로그, 에러 로그 형식, 업타임/알림
4. **통합 테스트 보강**: 완료/랭킹/업적 같은 핵심 흐름의 자동 테스트 (전환 후 회귀 방지)
